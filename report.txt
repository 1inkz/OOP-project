1 Introduction

This project presents the development of a command-line interface (CLI) life simulation game inspired by The Sims. The game is implemented in Java with a strong object-oriented architecture and emphasizes system interaction, modularity, and simulation logic rather than graphics. The design objective is to demonstrate OOP fundamentals in a maintainable, extensible codebase while delivering a complete and playable simulation experience.

1.1 Objectives

The project objective is to recreate core Sims-like mechanics as a text-based Java application, with software quality guided by OOP and test-driven validation practices. The implementation models Sims, pets, time, needs, jobs, banking, assets, location-based activities, and risk systems (including casino gameplay) as interacting domain objects. The CLI is organized into manager classes so gameplay remains understandable and scalable.

1.2 Core Gameplay Overview

Players control one or more Sims and guide daily life decisions: earning income, maintaining needs, managing finances, and investing in assets. Strategic pressure comes from time progression, need decay, and monetary constraints.

Key gameplay characteristics:
- Multiple Sim support with active Sim switching
- Need-driven survival (Hunger and Energy can become lethal if neglected)
- Job-based income progression and role-specific work locations
- Financial subsystem with cash, deposits, loans, and repayment pressure
- Asset subsystem (Car, House, Hotel) with tangible gameplay effects
- Pet subsystem with care responsibilities and trade-offs
- Location-specific action menus, including Casino with risk mechanics

1.3 Scope of Implementation

The project scope covers a complete terminal simulation loop with persistent save/load support. Implemented systems include:
- Sim creation and multi-Sim management
- Real-time/game-time advancement and hourly decay
- Need effects, critical-event policies, and penalties
- Employment and skill progression
- Banking and loan enforcement
- Asset ownership, maintenance, and repossession behavior
- Pet interactions and lifecycle management
- Extended location content (Restaurant, Hospital, Pet Store, Casino, etc.)

The scope intentionally excludes a graphical UI and advanced social-AI systems, prioritizing robust simulation mechanics and maintainable architecture.

2.3 Main Menu Navigation

Gameplay flow is menu-driven:
- Start Menu -> Sim Management -> Active Sim Main Menu
- Main menu provides status viewing, travel, location actions, jobs, assets, time passing, save/quit flow

This hierarchy reduces ambiguous input and keeps interactions context-specific.

2.3.1 Create/Select Sim

Players create Sims by selecting type (Child, Adult, Elder) and assigning a name. Multiple Sims can coexist; control can be switched strategically.

2.3.2 Daily Actions (Work/Eat/Sleep/Interact)

Daily actions are location-dependent. For example:
- Work appears where job location rules allow
- Home enables critical recovery actions
- Restaurant, Park, and other places expose their own action sets

Each action advances game time, so planning requires balancing progress with survival needs.

2.3.3 Asset Management (Buy/Sell Car/House)

Asset Operations allows buying/selling based on available funds and loan constraints. Effects include:
- Car: reduces travel fatigue but introduces maintenance responsibilities
- House: unlocks reliable survival actions
- Hotel: enables passive income strategy

2.3.4 Loan & Repayment Rules

Loans are capped and governed by overdue checks. Borrowing helps short-term growth but introduces medium-term risk if repayment is ignored.

2.3.5 Job Switching & Level Progression

Job switching is supported and job levels are tracked independently, preserving progression context across role changes. Work outcomes influence earnings and growth trajectory.

2.3.6 Save/Load Game Progress

Players can save and reload progress. State persistence includes Sims, time, needs, jobs, finances, assets, and pets.

2.4 Win/Lose Conditions

There is no single fixed win screen. Success is measured by sustained survival, stable needs, and long-term economic growth. A Sim is eliminated if survival conditions are breached; game continuity depends on the remaining Sims.


3 System Overview & Architecture

3.1 System Architecture Diagram

At runtime, Main initializes Game and ConsoleUI. Game acts as the orchestration facade over dedicated managers, while the UI layer forwards user intent to domain services.

Textual architecture diagram:
User Input
-> ConsoleUI
-> UI Managers (MenuUIManager / SimUIManager / BusinessUIManager)
-> Game (facade)
-> Core Managers (SimManager / LocationManager / TimeManager / ActionExecutor / LoanManager)
-> Domain Objects (Sim, Job, BankAccount, Assets, Pets, Location Actions)
-> Output Messages / Updated State
-> ConsoleUI display

Persistence boundary:
SaveGame <-> savegame.txt, invoked through menu actions and guarded exit flow.

Stepwise interaction sequence:
1) ConsoleUI receives a menu choice.
2) The relevant UI manager validates input and builds an action request.
3) Game routes the request to the appropriate manager/action.
4) Domain objects update money, needs, time, assets, and status.
5) Policies (need-crisis checks, loan checks, daily events) run after state transitions.
6) The resulting messages and current state are printed to the console.

3.2 Core Module Breakdown

3.2.1 CLI Interface Module (Console UI)

ConsoleUI runs the game loop and delegates specialized interactions to UI manager classes:
- MenuUIManager
- SimUIManager
- BusinessUIManager
- Input/UIHelper support classes

This preserves clear separation between presentation and domain logic.

3.2.2 Sim Entity Module (Sim/Needs)

Sim is the central domain entity but internally delegates responsibilities to component classes (stats, banking, employment, assets, pets), reducing monolithic complexity and improving maintainability.

3.2.3 Job & Career Module (Job/Job Factory)

Job is modeled through an interface and concrete implementations. JobFactory centralizes object creation and keeps UI/domain logic decoupled from concrete job classes.

3.2.4 Asset & Loan Module (Car/House/Banking System)

Assets and financial obligations are modeled as coordinated but separated concerns. BankingSystem governs deposits/withdrawals/loan flow while asset components control ownership, costs, and liquidation behavior.

3.2.5 Game State Module (Game/Clock/SaveGame)

Game coordinates:
- SimManager
- LocationManager
- TimeManager
- ActionExecutor
- LoanManager

GameClock and time policies drive world progression. SaveGame and persistence support session continuity.

3.3 Data Flow & Interaction

Input moves from CLI to Game orchestration, then into specialized managers and domain objects. Time advancement, need decay, policy checks, and loan checks run as integrated update cycles. Output is returned as user-readable status and action feedback.


4 Object-Oriented Design Decisions

4.1 Encapsulation

4.1.1 Sim Class: Encapsulation of State & Behaviour

Sim exposes meaningful operations while keeping internal state transitions controlled through component APIs. This avoids unsafe direct mutation from external modules.

4.1.2 Banking System: Isolation of Loan/Deposit Logic

Financial logic is encapsulated in banking classes, reducing leakage of monetary rules into unrelated gameplay classes.

4.2 Inheritance

4.2.1 Sim Hierarchy (ChildSim/AdultSim/ElderSim)

Sim subtypes share common behavior but allow controlled specialization (e.g., decay/work behavior differences by life stage).

4.2.2 Job Hierarchy (Job/ChefJob/DoctorJob)

Jobs implement a common contract while encapsulating profession-specific salary and work-location rules.

4.3 Polymorphism

4.3.1 Job Salary Calculation

Polymorphic job implementations provide role-specific salary behavior through shared interface methods.

4.3.2 Sim Hourly Decay

Decay and survival behavior are resolved via subtype/component behavior, avoiding large type-checking blocks.

4.4 Abstraction

4.4.1 Abstract Sim Class

Core Sim behavior is abstracted so each life stage remains a coherent specialization over shared mechanics.

4.4.2 Interface Design (Action/Job Interface)

Action and Job abstractions allow extensible behavior composition. New features (e.g., casino actions) can be added without refactoring core execution flow.

4.5 Design Patterns

4.5.1 Factory Pattern (JobFactory)

Factory centralizes job construction and keeps creation logic consistent.

4.5.2 Command Pattern (Action)

Actions are modeled as executable command objects selected by context, enabling modular activity expansion.

4.5.3 Singleton Pattern (Game/Clock)

The runtime session owns exactly one Game instance, created in Main and shared across UI managers. Game owns the single GameClock used by TimeManager for all time progression. This design guarantees one authoritative world state and one authoritative time source per session, preventing state divergence across menus and actions.

4.6 Key Design Trade-offs

Main trade-off: balancing modularity with class count complexity. The project favors modular managers/components for maintainability and extension safety. Additional trade-offs balance realism against playability (e.g., strict but playable financial and survival systems, risk-based casino mechanics).


5 Core Feature Implementation Details

5.1 Job Level System (Independent Career Levels)

Each Sim maintains job progression with role continuity. Switching jobs does not collapse all progression context, supporting strategic role changes.

5.2 Loan & Overdue Rules (60/80 Day Penalty Logic)

Loan flow includes staged overdue penalties and escalation behavior, enforcing financial discipline over long horizons.

5.3 Asset Repossession & Location Reset

When obligations fail, repossession logic can remove assets and normalize state to prevent invalid gameplay scenarios.

5.4 Save/Load Compatibility (New/Old Save File Support)

Persistence logic supports robust loading behavior and defensive handling of evolving save structures.

5.5 Dynamic Notification System (Role-Specific Alerts)

System surfaces contextual alerts (critical needs, financial warnings, time pressure) to improve decision quality while minimizing unnecessary noise.

7 Conclusion & Future Improvements

7.1 Project Summary

The project successfully demonstrates practical OOP design and TDD-oriented validation in a non-trivial simulation domain. The resulting system is modular, testable, and extensible, with clear separation of concerns across UI orchestration, domain entities, policy layers, and persistence.

7.2 Potential Enhancements

Potential next-phase improvements include:
- Richer relationship/social systems
- More dynamic random events and quest chains
- Expanded pet AI and interactions
- Additional locations and career tracks
- Optional difficulty profiles and balancing presets
- Optional graphical client while preserving domain core

Overall, the implementation meets its educational and engineering objectives. It applies core OOP principles (encapsulation, inheritance, abstraction, and polymorphism), uses pattern-driven architecture for extensibility, and maintains delivery confidence through continuous automated testing.
